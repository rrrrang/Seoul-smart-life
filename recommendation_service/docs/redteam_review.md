# Red Team 재검토 결과

검토일: 2026-10-21. 대상: 현재 backend_handoff와 로컬 .publish-repo/backend·database 사본. 이번 검토는 외부 API·실제 DB에 접속하지 않았고 키를 읽지 않았다. 보고서 외 제품 코드는 수정하지 않았으며 Git 업로드도 하지 않았다.

## 결론

가중평균 계산과 쾌적 구단위 참고값 연결은 구현되어 있다. 기존166개 테스트는 이번 재실행에서도 통과했다(166 passed in14.23s). 그러나 기존 테스트가 다루지 않은 P2 검증 결함3건과 서비스 연동 미완료를 발견했다. 무결점·운영준비완료로 판단하면 안 된다.

## P2-1: 기존 Pydantic 객체의 필드 재검증 우회 — 수정 전

schemas.py Contract 설정에 revalidate_instances가 없다. model_copy(update=...) 또는 검증을 우회한 중첩 객체를 전달하면 model_validate(instance)가 필드 검사를 다시 하지 않는다. CategoryScores(safety=50).model_copy(update={'safety':1000})을 safety-only 계산에 전달하면 오류가 아니라100.0으로 clipping된다. RecommendationRequest().model_copy(update={'top_k':0})도 빈 추천으로 수락한다.

정상 JSON DTO를 검증해 전달하는 경로의 직접 취약점과는 구분된다. 그래도 공개 함수가 재검증을 보장하려면 중첩 객체까지 재검증하는 설정/입구 검증과 회귀 테스트가 필요하다. 최소 재현: tests가 아니라 메모리 스크립트에서 수행했으며 파일 변경은 없다.

## P2-2: 잘못된 min_scores가 조용히 무시됨 — 수정 전

snapshot_service.py recommend_snapshots는 min_scores or {}로 조건을 기본값으로 바꾼다. [],False,0,''를 전달하면 모두 정상TOP5를 반환하는 것을 재현했다. 잘못된 자료형은422로 연결될 입력 검증 오류여야 한다. None만 기본값으로 처리하고 나머지는 명시적으로 검증해야 한다.

## P2-3: LLM 명시 가중치 누락값을1로 채움 — 수정 전

PreferenceDraft.weights가 일반Weights를 사용해 weights={'safety':100} 같은 불완전한 명시응답에 나머지 영역을1씩 채운다. MockTransport 독립 검토에서 재현했다. provider schema는 다섯키를 요구하지만 로컬검증은 기본값을 적용한다. LLM 명시가중치용 필수키 계약이 필요하다. 자연어 질문 UI는 제거했으므로 현재 슬라이더 추천의 직접 영향은 없다. 호환용 공개 함수는 남아 있으므로 미해결로 기록한다.

## DB/API 연결: 아직 미완료

현재 전달물은 JSON/CSV 스냅샷을 읽으며 PostgreSQL 조회 repository가 없다. 실제 서비스에서는 DB에 저장된 평가점수와 메타데이터를 조회해 추천입력으로 만드는 연결이 필요하다. 데이터·백엔드 담당 범위이므로 이번 리뷰에서 DB 스키마·엔드포인트를 수정하지 않았다.

로컬 .publish-repo/backend/app/main.py는 app.mock_data의 MOCK_SCORES를 사용한다. 주석과 입력 구조는 행정동10자리코드를 사용한다. 추천의region_code6자리/sigungu_code5자리 계약과 그대로 연결할 수 있다고 판단할 수 없다. 현재원격/운영DB상태는확인하지않았다.

로컬DDL dim_region.region_code는VARCHAR(10)이다. 이는최대길이이므로6자리저장도가능하며, 컬럼길이만으로실제값이10자리라고단정하지않는다. 서버의실제값과지역마스터매핑을확인해야한다. 코드앞/뒤를잘라서맞추지않는다. 요청한프로젝트기준식별자는6자리region_code이다.

DB 저장/조회 계약에는 최소 지역식별자·영역별0~100점·점수버전·영역별평가기준기간·원본공간단위·출처·추정/보간/승인상태를보존해야한다. 단순점수만저장하면쾌적자치구참고값을동별관측값으로오해시킬수있다. 사용자별가중치는원본점수를덮어쓰지않고추천요청에서적용한다. 조회정책은같은배포본/버전으로맞추고갱신주기/캐시무효화를정해야한다.
